## 1. 系统架构与数据模型

### 1.1 功能与角色

| 功能 | 管理员 | 教师 | 学生 |
|---|:--:|:--:|:--:|
| 录入成绩 | ✅ | ✅ | ❌ |
| 修改成绩 | ✅ | ✅ | ❌ |
| 修改学生信息（姓名/班级） | ✅ | ❌ | ❌ |
| 删除记录 | ✅ | ❌ | ❌ |
| 多条件查询 | ✅ | ✅ | 仅本人 |
| 统计分析 | ✅ | ✅ | 仅本人 |
| 保存文件 | ✅ | ✅ | ❌ |

两种运行模式共用同一套内存结构与算法：

- **控制台模式**：`main.c` 菜单 → 直接调用 `list_*`；
- **页面模式**：`webui.c` 内置 HTTP 服务器 → `/api/*` → 调用同一批 `list_*`。

### 1.2 记录模型：把「成绩」做成事实表

```c
typedef struct Student {
    char  id[MAX_ID_LEN];           // 学号，16
    char  name[MAX_NAME_LEN];       // 姓名，32
    char  className[MAX_CLASS_LEN]; // 班级，32
    char  term[MAX_TERM_LEN];       // 学期，16
    char  course[MAX_COURSE_LEN];   // 课程，32
    float score;                    // 成绩
} Student;                          // src/student.h:31-38
```

**设计取舍**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 一条记录 = 一个学生的全部课程（二维表） | 学生信息不冗余，改名一次搞定 | 课程数不定，C 里要变长数组；按课程查询要遍历内层 |
| B. 一条记录 = 一个学生的一门课（本项目） | 定长结构、按任意字段线性筛选简单、统计直接拍平 | 姓名/班级冗余，改名需批量同步 |

选 B 的理由：课程设计的核心是**链表 + 查找 + 排序**，B 让每条记录独立、结构定长、文件一行一条，最简单也最不容易出错。

### 1.3 内存结构

```

                │
                └── 每个 Node 24 + 1 字节指针开销，记录体 ~= 132 字节

哈希索引（静态数组，256 桶）：
  s_buckets[0]   → NULL
  s_buckets[10]  → IdxEntry("230101", →第一个 230101 节点) → NULL      ← 实际算出的桶号

  ...
```

## 2. 线性表：单向链表

### 2.1 为什么用链表而不是顺序表

| 操作 | 顺序表 | 单向链表 |
|---|---|---|
| 按位访问 | O(1) | O(n) |
| 已知位置插入/删除 | O(n)（搬移） | O(1)（改指针） |
| 头部插入 | O(n) | O(1) |
| 扩容 | realloc + 拷贝 | 天然 |
| 缓存局部性 | 好 | 差 |

本系统的真实负载是「**读多写少、按内容查、不按位访问**」：

- 查询必须遍历全表（顺序表也一样要扫），链表的 O(n) 不吃亏；
- 录入/删除是主要写操作，链表不需要搬移；
- 规模在千级，缓存局部性差异可忽略；
- 课程设计明确要求练习链表。

### 2.2 节点定义

```c
typedef struct Node {
    Student data;        // 记录本体
    struct Node* next;   // 后继指针
} Node;                  // src/list.h:8-12
```

**不带头结点（dummy head）**：`g_head` 直接指向第一个元素。好处是结构简单；代价是**所有涉及头部的操作都要特判**（删除头节点、头插）。

### 2.3 尾插法

`src/list.c:20-38`

```c
Node* list_insert_tail(Node* head, Student s) {
    Node* node = malloc(sizeof(Node));
    if (!node) return head;              // 分配失败：保持原表

    node->data = s;
    node->next = NULL;

    if (head == NULL) return node;       // 空表：新节点即表头

    Node* p = head;
    while (p->next != NULL) p = p->next; // 走到最后一个节点
    p->next = node;
    return head;
}
```

**为什么返回新头指针**：空表插入会改变 `head`，而 C 没有引用参数，只能靠返回值回传。调用方统一写 `head = list_insert_tail(head, s);`。

**成本推导**：第 i 次插入要走 i−1 步，建 N 条表的总步数

```
0 + 1 + 2 + ... + (N−1) = N(N−1)/2
```

| N | 指针跳转次数 | 量级 |
|---|---|---|
| 13（当前示例数据） | 78 | 可忽略 |
| 1,000 | 499,500 | 可忽略 |
| 10,000 | 49,995,000 | 明显卡顿 |
| 100,000 | 4,999,950,000 | 不可接受 |

**改进**：维护尾指针 `tail`，插入降为 O(1)，总建表 O(N)：

```c
Node* list_append(Node** phead, Node** ptail, Student s) { ... }
```

（代价：删除尾节点后 `tail` 失效，需要回退或改双向链表。）

**为什么仍然选尾插**：文件加载要求保持原始顺序（便于比对、导出），头插会整体逆序。

### 2.5 查找

**按学号**（`src/list.c:42-48`）：

```text
for p in list:
    if strcmp(p->data.id, id) == 0: return p
return NULL
```

**按复合键**（`src/list.c:50-58`）：`学号 + 学期 + 课程` 三字段全等。

```text
if (strcmp(id) == 0 && strcmp(term) == 0 && strcmp(course) == 0) return p
```

C 的 `&&` 短路：第一个字段不等就不再比较后两个，平均比较次数约 1 + 1/|Σ|。

**为什么用复合键**：同一个人同一学期有多门课；只按学号定位不到唯一记录。

**复杂度**：O(n·L)，L 为字段长度。n=13 时最坏 13 次 `strcmp`。

### 2.6 删除：双指针法

`src/list.c:67-88`

```c
Node* list_delete_one(Node* head, const char* id, const char* term,
                      const char* course, int* deleted) {
    Node *prev = NULL, *cur = head;
    *deleted = 0;

    while (cur != NULL) {
        if (strcmp(cur->data.id, id) == 0
            && (term   == NULL || term[0]   == '\0' || strcmp(cur->data.term, term) == 0)
            && (course == NULL || course[0] == '\0' || strcmp(cur->data.course, course) == 0)) {

            if (prev == NULL) head = cur->next;   // ① 删头节点
            else              prev->next = cur->next; // ② 删中间/尾节点

            free(cur);
            *deleted = 1;
            return head;
        }
        prev = cur;
        cur = cur->next;
    }
    return head;
}
```

**图解**：

```
删除中间节点 B：
      prev        cur
       ↓           ↓
  [A] ───────► [B] ───────► [C]
                 
  执行 prev->next = cur->next 后：
  [A] ─────────────────────► [C]        B 被 free

删除头节点 A：
  head ──► [A] ──► [B]
  执行 head = cur->next 后：
  head ──────────► [B]
```

**三个必须特判的点**：

1. **空表**：`cur == NULL`，循环不进入，返回原 head；
2. **删头**：`prev == NULL`，必须改 `head` 本身（C 里通过返回值）；
3. **找不到**：`*deleted = 0`，调用方据此判断。

**空字符串语义**：`term`/`course` 传 `""` 表示「该维度不限制」，于是可以「删该生全部记录」。控制台用循环反复调用直到 `deleted == 0`：

```c
for (;;) {
    g_head = list_delete_one(g_head, id, term, course, &deleted);
    if (!deleted) break;
}
```

k 条匹配时总成本 **O(k·n)**（每次从头扫）。

### 2.7 修改

**改成绩**（`src/list.c:92-99`）：先 `list_find_record` 定位，再改 `score`，O(n)。

**改学生信息**（`src/list.c:101-117`）：

```c
Node* p = list_find_by_id(head, id);
if (p == NULL) return 0;
for (; p != NULL; p = p->next) {     // 注意：从这里一直扫到表尾
    if (strcmp(p->data.id, id) != 0) continue;
    if (newName && newName[0])  strncpy(p->data.name, newName, MAX_NAME_LEN - 1);
    if (newClass && newClass[0]) strncpy(p->data.className, newClass, MAX_CLASS_LEN - 1);
    p->data.name[MAX_NAME_LEN - 1] = '\0';
    p->data.className[MAX_CLASS_LEN - 1] = '\0';
}
return 1;
```

**要点**：

- 同一学号的记录可能在链表中**不相邻**（文件里按课程排列，但用户可能穿插插入），所以不能「找到第一条后连续改到学号变化为止」，必须扫到表尾；
- `strncpy` 不保证补 `'\0'`（源串超长时），手动补终止符；
- 空字符串表示「不修改该字段」。

**复杂度**：O(n)。

### 2.8 遍历类操作

| 函数 | 位置 | 说明 | 复杂度 |
|---|---|---|---|
| `list_count` | `src/list.c:121-127` | 计数 | O(n) |
| `list_print_all` | `src/list.c:129-139` | 定宽打印 | O(n) |
| `list_destroy` | `src/list.c:141-148` | 逐个 free，先存 next 再 free | O(n) |

```c
void list_destroy(Node* head) {
    while (head != NULL) {
        Node* next = head->next;   // 必须先保存
        free(head);
        head = next;
    }
}
```

### 2.9 链表正确性的四个易错点

| 场景 | 错误写法 | 后果 |
|---|---|---|
| 删除头节点 | 只改 `prev->next`，忘了 `head` | 头节点泄漏，后续遍历从已 free 内存开始 |
| 释放顺序 | 先 `free(cur)` 再读 `cur->next` | 读已释放内存（UB） |
| 空表插入 | 直接 `head->next = node` | 空指针解引用 |
| 重复删除 | 忘记把 `*deleted` 复位 | 循环删空表后继续访问 |

## 3. 哈希索引：FNV-1a + 链地址法

### 3.1 动机

按学号查是最高频的操作（登录后查本人、录入前查重）。链表 O(n) 在 n=10⁴ 时每次要跳 5000 次。哈希表把平均查找降到 O(1+α)。

### 3.2 FNV-1a 哈希函数

`src/index.c:17-25`

```c
static unsigned int hash_id(const char* id) {
    unsigned int h = 2166136261u;          // offset basis（FNV 约定）
    while (*id != '\0') {
        h ^= (unsigned char)(*id++);       // 先异或
        h *= 16777619u;                    // 再乘 FNV 素数（uint32 自然溢出 = mod 2^32）
    }
    return h % INDEX_BUCKETS;              // 折叠到 256 个桶
}
```

**为什么用 FNV-1a**：

- 只用一次异或 + 一次乘法，比 CRC/ MD5 快一个量级；
- 对短字符串（学号 6~10 位）分布均匀；
- 无查表、无动态内存，`static` 纯函数，线程安全。

**为什么先异或再乘**（FNV-1a 与 FNV-1 的区别）：FNV-1 是先乘后异或，最后一位字节只参与异或不参与乘法，雪崩性差；1a 让每个字节都经过乘法扩散。

**无符号溢出的合法性**：C 标准规定无符号整型运算按 2³² 取模，不是 UB，正是我们需要的。

### 3.3 冲突处理：链地址法

```c
typedef struct IdxEntry {
    char id[MAX_ID_LEN];       // 关键字副本
    Node* node;                // 指向链表中该学号的第一条记录
    struct IdxEntry* next;     // 同桶冲突链
} IdxEntry;

static IdxEntry* s_buckets[INDEX_BUCKETS];   // 256 个桶，静态数组
```

```
桶 10:  [230101] → NULL
桶 81:  [230104] → NULL
桶 119: [230102] → [250101] → NULL     ← 若发生冲突，头插成链
```

**为什么不用开放定址法**：开放定址删除需要墓碑标记、装填因子高时性能骤降；链地址法删除简单（摘链）、装填因子可 >1、实现更短。

### 3.4 建索引

`src/index.c:27-57`

```text
index_build(head):
    index_destroy()                       // 清空旧索引
    for p in list:
        b = hash_id(p->id)
        if 桶 b 中已存在相同 id: continue  // 同学号只登记一次
        e = malloc(IdxEntry)
        e.id = p->id; e.node = p; e.next = s_buckets[b]; s_buckets[b] = e
        count++
    return count
```

**为什么只登记第一条**：同一学号有多门课，查「本人所有成绩」时从第一条顺链走即可；索引只负责定位起点。

**桶分布实测**（示例数据 6 个学号）：

| 学号 | FNV-1a（十进制） | 桶号 h % 256 |
|---|---|---|
| 230101 | 3044103690 | **10** |
| 230102 | 3027326071 | **119** |
| 230103 | 3010548452 | **228** |
| 230104 | 2993770833 | **81** |
| 230105 | 2976993214 | **190** |
| 250101 | 2977623544 | **248** |

6 个学号落在 6 个不同桶，无冲突。连续学号只差最后一位，哈希值相差接近 FNV 素数，取模后被打散——说明**低位变化能被乘法扩散到高位**。

### 3.5 查找与负载因子

`src/index.c:59-68`

```text
index_lookup(id):
    if id 为空: return NULL
    b = hash_id(id)
    for e in 桶 b 的冲突链:
        if strcmp(e->id, id) == 0: return e->node
    return NULL
```

- 平均查找长度 **1 + α/2**（成功查找），α = N / 256；
- 本项目 N ≈ 13 → α ≈ 0.05，几乎必然一次命中；
- N = 10,000 → α ≈ 39，链长 39，退化为 O(39)，仍远好于 O(10⁴)。

**为什么是 256**：2 的幂便于编译器把 `% 256` 优化成 `& 255`（GCC/Clang 对无符号取模会做此优化）；而 256 桶 × 8 字节指针仅 2KB 静态内存。

### 3.6 索引一致性：写后重建（已实现）

若 `index_build` 只在 `main()` 启动时调用一次，之后：

- 新增记录 → 索引里没有；
- 删除记录 → 索引里存的是**已 free 的节点指针**（悬空）；
- 修改学号（本系统不支持）→ 键值错。

**现行做法**：所有改变链表结构的写操作后立即重建——

| 写操作 | 重建位置 |
|---|---|
| 控制台录入 | `flow_add`：`list_insert_tail` 后 `index_build(g_head)` |
| 控制台删除 | `flow_delete`：删满后 `index_build(g_head)` |
| 页面录入 | `api_add`：插入后 `index_build(*ppHead)` |
| 页面删除 | `api_delete`：删除后 `index_build(*ppHead)` |

修改成绩/姓名班级不改节点归属，无需重建。Web 服务是单线程 accept 循环，重建无并发问题。

**消费端兜底**：`list.c` 的 `find_start` 拿 `index_lookup` 结果作为扫描起点，未命中（学号不存在或索引尚未建立）时回退整表遍历，正确性不依赖索引新鲜度；因写后必重建，索引中的节点指针必然挂在链表上。

### 3.7 与其它方案的对比

| 方案 | 查找 | 插入 | 删除 | 内存 | 实现量 |
|---|---|---|---|---|---|
| 链表遍历 | O(n) | O(1)* | O(n) | 最小 | 已实现 |
| 哈希索引（链地址） | O(1+α) | O(1) | O(1)+写后重建 | +2KB | 中（已接入查找） |
| 平衡树（AVL/红黑） | O(log n) | O(log n) | O(log n) | 中 | 大 |
| 跳表 | O(log n) 期望 | O(log n) | O(log n) | 中 | 大 |

*已知尾指针时。

## 4. 排序：三种实现

### 4.1 需求来源

1. 统计页要按分数降序排名 → 需要排序；
2. 表格点表头要按任意列排序 → 前端排序。

### 4.2 控制台：简单选择排序

`src/main.c:81-90`

```c
for (int i = 0; i < n - 1; i++) {
    int max = i;
    for (int j = i + 1; j < n; j++)
        if (arr[j].score > arr[max].score) max = j;
    if (max != i) { Student t = arr[i]; arr[i] = arr[max]; arr[max] = t; }
}
```

**思想**：每轮在未排序区间 `[i, n)` 中选最大者，放到位置 i。

**真实数据演算**（高等数学，6 条，初始顺序 = 文件顺序）：

```
初始: [92.0, 55.5, 88.0, 45.0, 76.5, 100.0]

i=0: 扫描 [0..5] 最大 = 100.0(下标5) → 交换 0↔5
     [100.0, 55.5, 88.0, 45.0, 76.5, 92.0]
i=1: 扫描 [1..5] 最大 = 92.0(下标5)  → 交换 1↔5
     [100.0, 92.0, 88.0, 45.0, 76.5, 55.5]
i=2: 扫描 [2..5] 最大 = 88.0(下标2)  → 不交换
     [100.0, 92.0, 88.0, 45.0, 76.5, 55.5]
i=3: 扫描 [3..5] 最大 = 76.5(下标4)  → 交换 3↔4
     [100.0, 92.0, 88.0, 76.5, 45.0, 55.5]
i=4: 扫描 [4..5] 最大 = 55.5(下标5)  → 交换 4↔5
     [100.0, 92.0, 88.0, 76.5, 55.5, 45.0]
完成
```

**复杂度推导**：

- 比较次数与初始顺序无关：`Σ_{i=0}^{n-2}(n-1-i) = n(n−1)/2`；
- 交换次数：最好 0（已降序），最坏 n−1（每轮都换）；
- 时间 O(n²)，空间 O(1)（原地）；
- **不稳定**：交换会跨过相等元素。

**n=13 时**：78 次比较，几乎无感。

### 4.3 页面：qsort + 三值比较器

`src/webui.c:190-195`

```c
static int cmp_score_desc(const void* a, const void* b) {
    float fa = ((const Student*)a)->score;
    float fb = ((const Student*)b)->score;
    return (fb > fa) - (fb < fa);      // 降序
}
```

**为什么不用 `return fb - fa`**：

1. 返回值是 `int`，两个 float 相减再截断，小差值会变 0（视为相等）；
2. `float` 溢出/NaN 时行为不可控；
3. `(a>b)-(a<b)` 严格输出 −1/0/1，语义清晰。

**注意**：`qsort` 的比较器参数是 `const void*`，必须先转回 `const Student*` 再取字段，不能直接解引用。

**复杂度**：标准库实现（通常为快速排序/内省排序 + 小数组插入排序），平均 O(n log n)，最坏 O(n²)（已排序且取首元素为轴时，现代实现用三数取中规避）。

### 4.4 前端：TimSort + 中文比较

`src/webui.c:373-377`

```js
const arr = [...lastData];
if (sortKey) arr.sort((a, b) => {
    const x = a[sortKey], y = b[sortKey];
    return (sortKey === 'score' ? (x - y) : String(x).localeCompare(String(y), 'zh')) * sortDir;
});
```

- V8 的 `Array.prototype.sort` 自 2019 年起为 **TimSort**（稳定，O(n log n)）；
- 字符串用 `localeCompare(..., 'zh')` 按拼音/笔画排序，而非字节序；
- `sortDir` 为 ±1，点同一表头取反。

### 4.5 三者对比

| 维度 | 选择排序 | qsort | TimSort |
|---|---|---|---|
| 典型时间 | O(n²) | O(n log n) | O(n log n) |
| 最坏时间 | O(n²) | O(n²) | O(n log n) |
| 稳定性 | 否 | 否 | 是 |
| 额外空间 | O(1) | O(log n) 栈 | O(n) |
| 适用 | 教学演示、n 小 | C 端通用 | 前端对象数组 |
| 本项目位置 | 控制台 | 页面统计 | 页面表格 |

**一致性缺口**：同一「排名」功能，控制台 O(n²)、页面 O(n log n)。数据量小时无感，但属于实现不统一，报告里应说明。

## 5. 排名：并列名次

### 5.1 定义

名次 = 1 + 比它严格高的人数（竞赛排名 / 1224 式）：

| 分数 | 100 | 92 | 92 | 85 | 80 |
|---|---|---|---|---|---|
| 名次 | 1 | 2 | 2 | 4 | 5 |

### 5.2 当前实现（O(n²)）

`src/main.c:104-111`、`src/webui.c:225-230`

```c
for (int i = 0; i < n; i++) {
    int rank = 1;
    for (int j = 0; j < i; j++)
        if (arr[j].score > arr[i].score) rank++;
    printf("%d", rank);
}
```

数组已降序，`j < i` 的元素分数都 ≥ 当前，因此只需统计严格大于者。

### 5.3 优化：单遍 O(n)

```c
rank[0] = 1;
for (int i = 1; i < n; i++)
    rank[i] = (arr[i].score == arr[i-1].score) ? rank[i-1] : i + 1;
```

**正确性**：若与前一个同分，则名次相同；否则前面 i 人全部严格更高，名次 = i+1。

**收益**：n=10⁴ 时，排名从 5×10⁷ 次比较降到 10⁴ 次。

### 5.4 三种并列口径

| 口径 | 分数 100/92/92/85 | 说明 |
|---|---|---|
| 竞赛排名（本项目） | 1 / 2 / 2 / 4 | 跳号 |
| 密集排名 | 1 / 2 / 2 / 3 | 不跳号 |
| 序位排名 | 1 / 2 / 3 / 4 | 不并列 |

## 7. 多条件查询

### 7.1 合取模型

五个条件全部为「与」，空条件视为恒真：

```text
result = { r ∈ R | (id="" ∨ r.id=id) ∧ (name="" ∨ r.name=name) ∧ ... }
```

### 7.2 短路求值

`src/webui.c:76-85`

```c
static int match(Node* p, const char* id, const char* name,
                 const char* className, const char* term, const char* course) {
    if (id[0]        && strcmp(p->data.id, id))                return 0;
    if (name[0]      && strcmp(p->data.name, name))            return 0;
    if (className[0] && strcmp(p->data.className, className))  return 0;
    if (term[0]      && strcmp(p->data.term, term))            return 0;
    if (course[0]    && strcmp(p->data.course, course))        return 0;
    return 1;
}
```

**条件顺序**：学号唯一性最高、姓名其次，放前面能最快排除。当前顺序（id → name → class → term → course）基本符合选择性从高到低。

**复杂度**：O(N·m·L)，m=5，L≈16。

### 7.3 两次扫描问题

`api_list` 为了先输出 `total`，扫了两遍：

```c
for (p = head; p; p = p->next) if (match(...)) total++;   // 第一遍：计数
for (p = head; p; p = p->next) if (match(...)) { ... }    // 第二遍：输出
```

**改进方案**：

1. 先序列化 data 到缓冲，最后回填 `total`（需要预留长度或二次 memmove）；
2. 用可增长缓冲，一次遍历同时计数与追加；
3. 前端不需要 total 时直接去掉。

### 7.4 若要支持大数据

| 方案 | 思路 | 代价 |
|---|---|---|
| 倒排索引 | 每个字段值 → 记录下标集合 | 写放大、需维护 |
| 位图 | 每个条件算位图，按位与 | 内存 O(N/8)/字段值 |
| 数据库 | 交给 SQLite | 引入依赖 |

课程设计规模不需要。

## 8. 字符串与协议解析

### 8.1 URL 解码

`src/webui.c:22-37`

```c
static void url_decode(char* dst, const char* src, int dstSize) {
    int di = 0;
    for (int i = 0; src[i] && di < dstSize - 1; i++) {
        if (src[i] == '+') dst[di++] = ' ';
        else if (src[i] == '%' && src[i+1] && src[i+2]) {
            char hex[3] = { src[i+1], src[i+2], '\0' };
            dst[di++] = (char)strtol(hex, NULL, 16);
            i += 2;
        } else dst[di++] = src[i];
    }
    dst[di] = '\0';
}
```

**算法**：单遍状态扫描，O(L)。

**边界缺陷**：`%G1` 这类非法十六进制，`strtol` 返回 0，会在字符串中间写入 `\0` 造成**截断**（而不是报错）。严格实现应校验 `isxdigit`。

### 8.2 查询串解析

`src/webui.c:42-57`

```text
先按 '&' 切分（strtok_s），再对每段按 '=' 切分
key 截断到 23 字节，value 经 url_decode 到 128 字节
最多 16 个参数，超出丢弃
```

**注意**：`strtok_s` 会**修改原缓冲区**（把分隔符改成 `\0`），因此 `target` 必须是可写内存（`recv` 的缓冲区，满足）。

### 8.3 文本解析

## 9. 认证与权限

### 9.1 登录全流程：从表单到会话

一次登录横跨三个模块（`webui.c` → `auth.c` → 会话链表），完整时序：

```text
浏览器                    webui.c                     auth.c
   │  GET /api/login?account=..&password=..
   │──────────────────────►│
   │                       │ api_login()                        webui.c:275-290
   │                       │──────► auth_login(acc, pwd, &s)    auth.c:76-99
   │                       │        ├─ 遍历 s_users，strcmp 账号 && 密码
   │                       │        ├─ 失败 → return 0
   │                       │        ├─ gen_token(s.token)         auth.c:68-74
   │                       │        ├─ Session{token, role, id, name}
   │                       │        └─ malloc + 头插 s_sessions
   │                       │◄────── 1
   │  {"code":0,"token":..}│
   │◄──────────────────────│
   │
   │  GET /api/list?token=..
   │──────────────────────►│ auth_verify(token, &sess)          auth.c:101-112
   │                       │──────► 遍历 s_sessions，strcmp
   │                       │◄────── 命中 / 未命中
   │                       │ 角色拦截 + force_param
   │  {"code":0,"data":[..]}│
   │◄──────────────────────│
```

**三次交互之后，身份只靠 token 维持**：密码不再出现在后续请求里——这是 token 机制的核心价值，减少凭据暴露面。

**会话生命周期**：

| 阶段 | 动作 | 位置 | 复杂度 |
|---|---|---|---|
| 签发 | 生成 token + 头插会话链 | `auth.c:76-99` | O(U) 验密 + O(1) 插入 |
| 校验 | 线性查会话链 | `auth.c:101-112` | O(S) |
| 销毁 | 双指针摘链 | `auth.c:114-127` | O(S) |

- U = 账号数，S = 同时在线会话数；课程设计场景都为个位数。
- 若 S 到万级，可把会话表换成哈希表（token → Session），校验降为 O(1)。

**登录失败的三种情况**（代码里都归为 `return 0`）：

| 情况 | 代码路径 |
|---|---|
| 账号不存在 | 遍历到表尾返回 0 |
| 密码错误 | 账号命中但 `strcmp` 不等，继续找后面（允许重复账号） |
| 空账号 / 空密码 | 函数入口直接 `return 0` |

**两个安全细节**：

1. `strcmp` 是短路的，比较时间与匹配前缀长度相关——本机服务可忽略，真实系统应用恒定时间比较；
2. 登录失败不区分「账号不存在」和「密码错误」，避免账号枚举（当前返回统一文案「账号或密码错误」，是正确的做法）。

**角色兜底**：`auth_load` 对非法角色值统一降级为学生（`auth.c:57`），防止 `users.txt` 被改坏后出现「无角色」导致的越权或崩溃。

## 10. 文件持久化

### 10.1 为什么用文本文件

| 方案 | 优点 | 缺点 |
|---|---|---|
| 文本文件（本项目） | 零依赖、记事本可看、便于交作业与调试 | 无事务、无索引、并发弱 |
| 二进制文件 | 紧凑、解析快 | 不可读、跨平台字节序问题 |
| SQLite | 事务、索引、并发 | 引入第三方库，偏离课程主题 |

课程设计重点是数据结构与算法，文本文件让「数据可见」，调试成本最低。

### 10.2 文件格式

```text
学号 姓名 班级 学期 课程 分数
230101 张三 计科2301 2025-2026-1 高等数学 92.0
```

- 空格分隔、一行一条、UTF-8 无 BOM；
- 字段宽度与结构体常量一一对应：`%15s %31s %31s %15s %31s %f`（`fileio.c:19-20`）；
- 分数用 `%.1f` 写出，读回 `float`。

**代价**：姓名/班级/课程里不能含空格。要支持空格，得改成 CSV（引号转义）或制表符分隔。

### 10.3 加载：从文件到链表

`fileio.c:9-29`

```c
while (fscanf(fp, "%15s %31s %31s %15s %31s %f",
              s.id, s.name, s.className, s.term, s.course, &s.score) == 6) {
    head = list_insert_tail(head, s);   // 尾插，保持文件顺序
    count++;
}
```

| 细节 | 作用 |
|---|---|
| `%15s` 等宽度限制 | 与字段数组长度匹配，防缓冲区溢出 |
| 返回值 `== 6` | 六个字段全读到才算一条，防止残缺行入表 |
| 尾插 | 保持文件顺序，便于导出比对 |
| `count` 出参 | 返回条数，用于启动提示 |

**两个缺陷**：

1. **遇错即停**：`fscanf` 格式不匹配时返回小于 6，循环直接结束——**一行损坏会导致后面所有记录丢失**；
2. **建表 O(N²)**：尾插每次都从表头走到表尾。

**改进（逐行解析 + 尾指针）**：

```c
char line[MAX_LINE_LEN];
while (fgets(line, sizeof line, fp) != NULL) {
    Student s;
    if (sscanf(line, "%15s %31s %31s %15s %31s %f", ...) == 6)
        head = list_append(&head, &tail, s);      // O(1)/条
    else
        fprintf(stderr, "跳过坏行: %s", line);     // 跳过而不是中断
}
```

### 10.4 写策略：追加 vs 全量重写

| 操作 | 方式 | 复杂度 | 写放大 | 风险 |
|---|---|---|---|---|
| 录入 | `fopen("a")` 追加 | O(1) | 1 行 | 中途崩溃 → 半行 |
| 修改成绩 | 全量重写 | O(N) | N 行 | 中途崩溃 → 文件截断 |
| 删除 | 全量重写 | O(N) | N 行 | 同上 |
| 手动保存 | 全量重写 | O(N) | N 行 | 同上 |

**写放大计算**：删除 1 条，N = 10,000 时重写约 10,000 行 × 60 字节 ≈ **600KB～1.3MB**。频繁删除时磁盘 I/O 成为瓶颈。

**为什么不全用追加**：文本文件改不了变长字段，修改/删除只能重写。

### 10.5 崩溃一致性

当前实现：

```c
FILE* fp = fopen(path, "w");      // ① 立即把文件截断为 0 字节
for (p = head; p; p = p->next) fprintf(fp, ...);   // ② 逐行写
fclose(fp);
```

若在 ① 之后、② 完成之前崩溃或断电：

- 文件已被截断 → **原数据全部丢失**；
- 只写了一半 → 文件残缺，下次只能读到前几条。

**原子替换方案**：

```text
1. 写 data/students.txt.tmp
2. fflush(fp) + fsync(fileno(fp))       // 数据真正落盘
3. rename("students.txt.tmp", "students.txt")   // 同分区上原子
```

- `rename` 在 POSIX 与 Windows（`MoveFileEx` + `REPLACE_EXISTING`）上都是原子的；
- 崩溃后要么是旧文件、要么是新文件，**不会出现半个文件**；
- 代价：需要 2 倍磁盘空间，多一次重命名（开销可忽略）。

### 10.6 并发与锁

- 服务端单线程 `accept`，请求串行处理 → **进程内无并发写**；
- 但文件是共享资源：用户用记事本改、或同时跑两个实例，就会互相覆盖；
- 当前**没有文件锁**，后写者赢；
- 改进：独占打开（Windows `FILE_SHARE_READ`）或锁文件 `.lock`。

### 10.7 数据恢复与校验

| 手段 | 做法 | 成本 |
|---|---|---|
| 备份 | 保存前把旧文件复制为 `.bak` | 一次复制 |
| 行校验 | 字段数必须为 6（已隐式实现） | 无 |
| 版本头 | 首行写 `#v1`，便于格式演进 | 低 |
| 操作日志 | 追加日志，崩溃后重放 | 高 |

**格式演进风险**：以后加字段时，老文件行数不足，`fscanf` 提前返回 → 整行被丢弃。加版本头可缓解。

## 11. HTTP 服务模型

### 11.1 单线程 accept 循环

`src/webui.c:540-563`

```text
for (;;) {
    client = accept(listenSock)          // 阻塞
    set SO_RCVTIMEO = 2000ms
    len = recv(client, req, 8191)
    if (len > 0) 解析请求行 → handle()
    closesocket(client)
}
```

- 一次只服务一个连接，简单但吞吐低；
- 浏览器会「预连接」但不发数据，若没有接收超时，单线程会被一个空连接**永久阻塞**——这是本项目最关键的工程细节。

### 11.2 请求解析

```c
sscanf(req, "%7s %2047s", method, target)
```

只接受 `GET`，其余返回 405（`Method Not Allowed`）。

### 11.3 短写处理

`src/webui.c:404-412`

```c
static void send_all(SOCKET sock, const char* buf, int len) {
    int sent = 0;
    while (sent < len) {
        int n = send(sock, buf + sent, len - sent, 0);
        if (n <= 0) break;
        sent += n;
    }
}
```

TCP 发送缓冲区满时 `send` 只发部分字节，必须循环。

### 11.4 绑定与访问控制

```c
addr.sin_addr.s_addr = htonl(INADDR_LOOPBACK);   // 127.0.0.1
```

只监听环回，外部机器无法连接；但本机任意进程可访问（令牌是唯一门槛）。

### 11.5 响应

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: N
Connection: close
```

`Connection: close` 简化实现（不维护 keep-alive 状态机），代价是每请求一次 TCP 握手。

## 16. 答辩问答

**Q1：为什么用链表而不是数组？**
记录频繁增删，链表改指针即可，不需搬移；查询本来就要全表扫描，链表的 O(n) 不吃亏；且课程设计要求练习链表。

**Q2：尾插法建表为什么是 O(N²)？**
每次插入都要从表头走到表尾，第 i 次走 i−1 步，总计 N(N−1)/2。

**Q3：那为什么不用头插？**
头插 O(1) 但会逆序，加载后与文件顺序不一致，调试和导出都不方便。

**Q4：删除节点要注意什么？**
三件事：空表判断、删头节点时改 head、free 前先保存 next。

**Q5：哈希怎么解决冲突？**
链地址法，256 个桶，桶内单链头插。平均查找 1+α/2。

**Q6：为什么选 256 个桶？**
2 的幂可优化取模；256×8B=2KB 内存可接受；α=N/256，千级数据几乎无冲突。

**Q7：索引怎么保持和链表一致？**
`index_build` 在启动时建一次，之后每次录入/删除后立即重建（写后重建）；重建是 O(n)，千级数据微秒级，牺牲重建开销换来查找链路全程命中索引。若索引未命中，`list.c` 会回退整表遍历，不影响正确性。

**Q8：排名怎么算的？**
先按分数降序，名次 = 1 + 前面严格更高的人数，同分并列、后续跳号（竞赛排名）。

**Q9：为什么排名是 O(n²)？**
对每个元素都回头数一遍。其实数组已有序，改成一趟比较相邻分数即可 O(n)。

**Q10：多条件查询怎么实现？**
线性扫描 + 五条件短路与；空条件跳过，任一不等立即返回。

**Q11：学生怎么防止越权？**
登录发 token，服务端校验角色；学生请求时用 `force_param` 把 `id` 改写成令牌里的学号，前端改参数无效。

**Q12：系统瓶颈在哪？**
批量导入的 O(N²) 和排名的 O(n²)。千级数据可接受，规模化需改尾指针、单遍排名，并把查询接到哈希索引上。

## 17. 桶排序与哈希桶辨析

### 17.1 两个「桶」不是一回事

代码里 `s_buckets[256]` 有 256 个桶，很容易被误认为「用了桶排序」。二者只是中文名都带「桶」：

| | 哈希桶（本系统 `s_buckets`） | 桶排序（Bucket Sort） |
|---|---|---|
| 类别 | **存储/查找结构** | **排序算法** |
| 目的 | 按 key 快速定位记录 | 把记录按值域排好序 |
| 分桶依据 | `hash(key) % 256` | 值域等分区间 |
| 桶内内容 | 冲突链（链表） | 待排序元素 |
| 桶内是否排序 | 否 | 是 |
| 复杂度 | 查找 O(1+α) | 平均 O(n+k) |

**答辩第一句**：“哈希桶是存储结构，桶排序是排序算法，本系统的排序用的是选择排序和 qsort。”

### 17.2 桶排序原理

```text
输入：n 个元素，值域 [min, max]，划分 k 个桶
1. 把 [min, max] 等分成 k 个区间
2. 元素按值落入对应桶
3. 每个桶内部单独排序（通常用插入排序）
4. 按桶的先后顺序拼接输出
```

**复杂度**：

- 平均 O(n + k)：分桶 O(n)、桶内近似 O(1)、拼接 O(k)；
- **最坏 O(n²)**：所有元素落入同一个桶，退化为桶内排序；
- 空间 O(n + k)；
- **稳定性**取决于桶内排序：用插入排序则稳定。

**成立前提**：元素在值域上**均匀分布**。若严重偏斜（例如 90% 的分数集中在 60–70），会退化成对一个大桶排序，优势消失。

### 17.3 本系统为什么特别适合

排序键是分数，值域固定 `[0, 100]` 且保留一位小数——这是桶排序最理想的输入：

```text
量化：q = round(score * 10)   →   q ∈ [0, 1000]
桶数：k = 1001
```

此时桶排序退化为**计数排序**（每个桶最多对应一个分数值），桶内不需要再排序：

```text
cnt[1001] = {0}
for r in records: cnt[q(r.score)]++            // 分桶 O(n)

seen = 0
for b from 1000 down to 0:                     // 降序扫描
    rank = seen + 1
    for each record with q == b:
        输出(rank)                             // 同桶同名次
    seen += cnt[b]
```

- 时间 **O(n + 1001)**；
- 额外空间 **O(1001)**（只存计数，不需存元素）；
- **天然稳定**：同分记录保持原有顺序；
- **名次顺带算出**，不需要「排序后再双重循环数名次」。

### 17.4 与现有实现对比

| 方案 | n=13 | n=1,000 | n=100,000 | 稳定性 | 额外空间 |
|---|---|---|---|---|---|
| 选择排序 | 78 次比较 | 5×10⁵ | 5×10⁹ | 否 | O(1) |
| qsort | 约 50 次 | 约 10⁴ | 约 1.7×10⁶ | 否 | O(log n) |
| 计数排序 | **1001 次初始化** | 2,001 | 1.01×10⁵ | **是** | O(1001) |

**关键结论**：k 固定为 1001，当 `n < k` 时，初始化 1001 个计数器的固定开销超过排序收益；只有 **n ≫ k** 时计数排序才明显更快。

所以「桶排序更快」这句话是有条件的：**快在 n 大、值域小且均匀**。

### 17.5 为什么当前没有采用

1. **规模小**：课程设计数据千级以内，qsort 毫秒级完成，用户无感；
2. **实现成本**：要处理量化取整、桶数组、并列名次、越界夹紧，代码量明显增加；
3. **通用性差**：值域或精度一变（如改成 10 分制、保留两位小数），桶数要跟着改，常量写死；
4. **教学定位**：选择排序 / qsort 是数据结构课程的标准内容，桶排序属于加分项。

### 17.6 如果要用：改造点

| 位置 | 改动 |
|---|---|
| `flow_stats` / `api_stats` | 用 `q = (int)(score * 10.0f + 0.5f)` 量化 |
| 排序 | 替换为 1001 个计数桶 + 降序扫描 |
| 排名 | 扫描时顺带累计 `seen`，O(n + k) |
| 边界 | `q` 夹紧到 `[0, 1000]`，防止 100.05 之类的越界 |

**浮点陷阱**：不能直接拿 `float` 做桶下标，必须先量化取整，否则 `60.0f` 与 `59.999999f` 会落进不同桶。

### 17.7 答辩话术

**问：你的哈希是不是桶排序？**
答：不是。`s_buckets` 是哈希桶，用于按学号查找；排序用的是简单选择排序和 qsort。

**问：能不能用桶排序做排名？**
答：能，而且本场景非常适合——分数值域固定、一位小数，量化成 0~1000 后就是计数排序，时间 O(n+1001)，还能顺带算出并列名次。

**问：那为什么不用？**
答：n 只有千级、桶数 k=1001，`n < k` 时初始化开销反而更大；qsort 已足够。数据到十万级时我会换成计数排序。

**问：桶排序稳定吗？**
答：取决于桶内排序；用插入排序或计数版本时稳定，正好满足同分并列的需求。

**问：桶排序最坏情况？**
答：所有元素落进一个桶，退化为 O(n²)。
